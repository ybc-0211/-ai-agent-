# Todo Agent 产品功能评估

本文档评估五个候选产品能力，不包含本轮功能实现。当前数据模型仍是：

```text
Task = { id, title, done }
```

Agent 只暴露 `list_tasks`、`create_task`、`complete_task`、`delete_task` 和 `respond`。因此所有新增能力都需要同时考虑 REST API、Agent 工具、数据兼容和测试，而不能只改前端文案。

## 1. 截止日期

### 用户场景

- “明天下午交报告”
- “今天有哪些任务到期？”
- “这件任务已经逾期了吗？”

### 数据结构变化

建议在任务上增加可选的日期字段：

```text
dueDate?: string  // YYYY-MM-DD，日期级截止
```

第一版建议只做日期，不做具体时刻，避免时区和“下午”等模糊表达带来的复杂度。数据库/JSON 中缺失字段表示无截止日期。

### API / 工具变化

- `POST /api/tasks`、`PATCH /api/tasks/:id` 增加可选 `dueDate`。
- `GET /api/tasks` 增加 `due=today|overdue|none` 过滤。
- `create_task` 增加可选 `dueDate`。
- `list_tasks` 增加可选 `due` 过滤。
- 是否需要 `update_due_date` 工具取决于是否允许在对话中修改截止日期；第一版可先只支持创建。

### 实现难度

**中等。** 难点不在字段，而在自然语言时间解析、日期校验、时区约定和“今天/逾期”的服务端计算。

### 对现有功能的影响

- 名称匹配逻辑不受影响；
- 清单输出需要增加截止日期；
- 需要明确完成时间与截止日期的关系；
- 旧的缺少 `dueDate` 的任务保持兼容。

### 测试要求

- 合法/非法日期；
- 无截止日期；
- 今天、明天、逾期边界；
- API 过滤；
- Agent 创建带截止日期的任务；
- E2E 验证“今天到期”查询。

## 2. 优先级

### 用户场景

- “把交报告设为高优先级”
- “先看高优先级任务”
- “按优先级排序，不要按创建顺序”

### 数据结构变化

```text
priority?: "low" | "medium" | "high"
```

缺失时按 `medium` 处理，避免旧任务迁移成本。

### API / 工具变化

- 创建/更新任务增加 `priority`；
- 清单支持按优先级排序；
- `create_task` 增加可选 `priority`；
- 可增加 `update_priority` 工具，或先允许在创建时指定。

### 实现难度

**低。** 枚举校验和排序逻辑简单，与现有 `done` 字段同级别。

### 对现有功能的影响

- 名称匹配、完成、删除逻辑不变；
- 清单输出和排序需要调整；
- 现有任务默认 medium，不破坏兼容性。

### 测试要求

- 枚举合法性；
- 默认值；
- 排序稳定性；
- API/tool 更新；
- E2E 自然语言设置和查询优先级。

## 3. 子任务

### 用户场景

- “准备面试”下面拆成“复习算法”“整理项目经历”“准备自我介绍”。
- 父任务完成前检查子任务是否完成。

### 数据结构变化

两条路线：

1. **扁平 parentId**：`parentId?: string`，所有任务仍在一个列表。
2. **嵌套 subtasks**：任务对象内嵌 `subtasks` 数组。

建议优先考虑扁平 `parentId`，因为可复用现有 TaskStore、REST 路由和 Agent 名称匹配；嵌套结构会显著增加读写和搜索复杂度。

### API / 工具变化

- 创建任务支持 `parentId`；
- 清单支持按父任务分组；
- 删除父任务需要明确是否级联删除；
- 完成父任务需要定义是否要求子任务全部完成；
- Agent 需要新增工具或参数，名称匹配要考虑父子同名情况。

### 实现难度

**高。** 数据关系、级联删除、完成规则、歧义处理和 UI 展示都会变复杂。

### 对现有功能的影响

- 删除、完成、查询语义都需要重新定义；
- 名称匹配可能命中父子多个任务；
- 现有测试需要大量扩展；
- 不建议在当前阶段先做。

### 测试要求

- 父子创建；
- 同名父子歧义；
- 级联删除/禁止删除；
- 父任务完成规则；
- API 过滤与 E2E。

## 4. 任务筛选和搜索

### 用户场景

- “只看未完成任务”
- “搜索包含‘报告’的任务”
- “查看所有高优先级任务”

### 数据结构变化

通常不需要新增任务字段；需要新增查询参数：

```text
GET /api/tasks?status=open&q=报告&priority=high
```

### API / 工具变化

- `GET /api/tasks` 增加过滤参数；
- `list_tasks` 增加 `status`、`query`、`priority` 等参数；
- Agent 需要把自然语言条件转为工具参数；
- 返回结果仍只包含标题、状态和新增的展示字段。

### 实现难度

**中等。** 单个过滤条件不难，难点是自然语言条件组合、结果排序和确保 Agent 不把过滤结果误当成完整清单。

### 对现有功能的影响

- 现有无参数查询必须保持返回全部任务；
- 名称匹配仍应基于真实任务，而不是过滤后的子集；
- 工具 schema 和测试会扩展。

### 测试要求

- 单条件和组合条件；
- 空结果；
- 非法过滤值；
- 过滤后的完成/删除仍按真实任务执行；
- E2E 自然语言筛选。

## 5. 任务状态管理

### 用户场景

- “这个任务正在做”
- “不要只显示完成/未完成，显示进行中”
- “把任务放回待办”

### 数据结构变化

从：

```text
done: boolean
```

扩展为：

```text
status: "todo" | "doing" | "done"
```

需要兼容旧数据中的 `done` 字段，或做一次性迁移。`done` 与 `status` 同时存在会产生双写和一致性问题。

### API / 工具变化

- `PATCH /api/tasks/:id` 支持状态；
- 完成工具需要改名为状态更新工具，或保留 `complete_task` 作为快捷方式；
- 清单输出和过滤需要支持三种状态；
- 前端只通过聊天展示状态，暂时没有独立看板。

### 实现难度

**中高。** 字段迁移和现有 API 兼容是主要风险；产品语义也比布尔完成更复杂。

### 对现有功能的影响

- 完成操作、排序、查询、筛选都会受影响；
- 现有测试需要覆盖旧字段兼容；
- Agent 工具名称和描述需要调整。

### 测试要求

- 旧 `done` 数据迁移；
- 三态转换；
- 完成快捷工具与状态更新的一致性；
- API/工具/E2E。

## 综合比较

| 功能      | 用户价值 | 实现难度 | 对现有功能影响 | 建议顺序 |
| --------- | -------- | -------- | -------------- | -------- |
| 优先级    | 高       | 低       | 低             | 1        |
| 截止日期  | 高       | 中       | 中             | 2        |
| 筛选/搜索 | 中高     | 中       | 中             | 3        |
| 状态管理  | 中       | 中高     | 高             | 4        |
| 子任务    | 中高     | 高       | 高             | 5        |

## 推荐优先实现的两个功能

### 第一优先：优先级

理由：

- 直接改善“先做什么”的决策；
- 数据结构简单，向后兼容；
- 可复用现有创建/查询/更新链路；
- 不改变名称匹配和删除语义。

简明实施方案：

1. 任务增加可选 `priority`，缺失默认 `medium`；
2. zod 和 REST API 增加枚举校验；
3. `create_task` 增加可选参数，`list_tasks` 按优先级稳定排序；
4. 清单输出显示优先级；
5. 补充 API、Agent 和 E2E 测试。

### 第二优先：截止日期

理由：

- 和优先级组合后能形成基本的任务规划；
- 日期级实现可控，不需要一次性引入复杂提醒系统；
- 能自然扩展“今天到期/逾期”查询。

简明实施方案：

1. 增加可选 `dueDate: YYYY-MM-DD`，缺失表示无截止日期；
2. 创建/更新 API 校验日期；
3. `create_task` 增加可选 `dueDate`，`list_tasks` 增加 `due` 过滤；
4. 清单显示日期并标记今天/逾期；
5. 先支持创建时设置，再评估是否增加独立修改工具；
6. 补充边界测试和 E2E。

## 暂不推荐本轮实现

- 子任务：会改变任务关系和删除/完成语义，应先完成优先级和截止日期的基座。
- 三态状态管理：需要决定是否迁移 `done`，风险高于收益。
- 完整前端任务面板：当前 UI 是聊天界面，新增复杂视图应另立设计任务。

## 实施约束

- 每个功能必须先更新数据结构、API 契约和工具 schema，再改 Agent 文案；
- 不把未实现字段写进 README 的“已实现功能”；
- 所有新增能力必须有单元/API/E2E 覆盖；
- 真实 DeepSeek Smoke 不应在普通 CI 中运行。
